# 测速记录提交与可选计时

测试者于 2026-10-14 确认：流媒体使用 YouTube 4K 画质，拖动进度条三次，分别观察恢复播放前的缓冲；ChatGPT 观察从发送消息到开始出现回答的等待。此日期是方法确认日，实际测试仍使用每条记录自己的日期。

## 日常提交

继续使用原五项格式，并附对应的 Speedtest 截图：

```text
机场名：
节点名称：
ChatGPT：
流媒体：
Speedtest 链接：
```

ChatGPT 状态为：流畅、轻微延迟、响应较慢、响应严重延迟、不可用。
流媒体状态为：流畅、轻微缓冲、缓冲明显、缓冲严重、不可用。

ChatGPT 按发送至开始出现回答的等待分档：≤5 秒 → 流畅（100）；>5–10 秒 → 轻微延迟（75）；>10–20 秒 → 响应较慢（50）；>20–30 秒 → 响应严重延迟（25）；超过 30 秒仍未开始回答或无法访问 → 不可用（0）。“未响应”提交时使用标准状态“不可用”。

日期、速度等从测速证据核对；本地网络、设备或客户端与默认环境不同时单独注明。

## 实际计时后可补充

```text
YouTube 视频地址：
三次拖动后至恢复播放的缓冲时间（秒，按第1/2/3次顺序）：
ChatGPT 发送至开始出现回答的等待（秒）：
ChatGPT 模型（如已记录）：
```

没计时或未保存的项目可省略。没有等待且确实观察到的 0 秒与未知不同；未知项保留为“未记录”。无法播放或无法获得回答时按实际状态提交，不能用 0 秒代替失败。完整回答耗时不填入首次响应等待。

入库时可在原记录上增加以下可选对象。下面是缺少精确秒数时的结构示例，不是实测结果：

```json
{
  "streamingTest": {
    "platform": "YouTube",
    "quality": "4K",
    "seekBufferingSeconds": [null, null, null]
  },
  "chatgptTest": {
    "firstResponseSeconds": null
  }
}
```

- `seekBufferingSeconds` 若填写，须恰好三项，按拖动次序保存；每项为非负有限秒数，未保存为 `null`。整组未记录时可省略这个字段。
- `firstResponseSeconds` 保存发送到开始出现回答的实际秒数，未知为 `null` 或省略；`model` 仅在确实记录时填写。
- `streamingTest.videoUrl` 可保存公开的 HTTP/HTTPS 视频地址。应用操作截图沿用原记录的 `evidenceImages: [{ label, path }]`，与 Speedtest 主截图分别标注。
- 两个对象都可省略，已有记录无需批量补写。字段由数据审计及构建校验；保存后在机场详情和测速中心的“记录详情”展示。

状态对应的分值和评分权重继续沿用公开规则。填写了精确首次响应秒数时，校验其与 ChatGPT 档位是否一致；冲突会提示核对，不静默改写状态。未保存秒数的旧记录继续按原状态计分，不从状态反推秒数。流媒体仍按实际观察提交定性状态，YouTube 播放结果不用于推断其他平台解锁。
